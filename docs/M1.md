# Milestone 1: Pipeline Skeleton

Started: 2026-10-23. Branch: `m1-pipeline`.

## Goal

Turn the single-docket monitor into a stage-based pipeline. It watches several cases incrementally within the CourtListener quota and emails one digest per recipient per run. No LLM yet; that is Milestone 2.

## Decisions

| Decision | Choice |
| --- | --- |
| Rewrite or evolve | Evolve. Existing safeguards (outbox, atomic writes, secret-safe logging) are reused. |
| LLM | Not in M1. The provider-neutral settings and adapter registry exist now. The analyzer comes in M2, with DeepSeek as the first provider. |
| Cross-case collector | Paused (it is manual-only already). The API quota goes to the pipeline. |
| Schedule | Every 2 hours. The old hourly workflow becomes manual-only. |

## API facts checked (T0)

From the CourtListener v4 documentation:

- Rate limits are 5/minute, 50/hour and 125/day per account, on rolling windows that apply at the same time.
- Filters combine through multiple query parameters. Ordering by `date_modified` or `id` uses cursor pagination through `next`; the `page` parameter does not work there.
- The default page size is not documented, so the code does not depend on it.
- `order_by=date_modified,id` with `date_modified__gte/__lt` already ran in production in the collector's cloud runs, with cursor pages validated.
- Whether 429 responses carry `Retry-After` is not documented. The pipeline pauses for 24 hours on any 429.

## Deployment checklist (owner)

1. Review and merge `m1-pipeline` into `main`. The legacy hourly schedule stops at merge.
2. Confirm the secrets listed in the README exist. `EMAIL_TO` is no longer used by the pipeline.
3. Locally, with `DATABASE_URL` in `.env`, add yourself and subscribe:
   `python -m src.admin --dotenv add-recipient you@example.com`, then
   `python -m src.admin --dotenv subscribe you@example.com 73132799`.
   Docket 73132799 resumes from the legacy monitor's last success.
4. Run **Run docket pipeline** with `dry_run` ticked. Expect status `ok`, roughly one request per docket, and no email.
5. Run it again without `dry_run`, then let the schedule take over.
6. Subscribe 3–5 active dockets (T11). Check the run summaries daily.

## Acceptance criteria

- Seven consecutive days of scheduled runs in the cloud.
- At least one digest triggered by a real docket change, with correct content and links.
- No duplicate email. Any `needs_review` item is investigated.
- Fewer than 100 CourtListener requests per day, according to the `api_requests` ledger.
- CI is green, including the PostgreSQL integration job.

## Known follow-ups

- If new events arrive between a failed status update and the next run, a digest can repeat items that were already accepted. This is rare and visible in `email_outbox`.
- Runs killed mid-way stay `running` in `pipeline_runs`.
- There is no unsubscribe link in emails yet. Recipients are managed through `src.admin`.
- For Milestone 2: LLM analyzer, evaluation set (`eval/labeled.jsonl`), token budget, preview-before-enable.
