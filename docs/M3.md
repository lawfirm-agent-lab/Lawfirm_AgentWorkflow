# Milestone 3: Reading Full Documents

Started: 2026-10-24. Branch: `m3-document-analysis`.

## Goal

Brief lawyers on the full text of a filed document, not just the one-line docket entry: what it asks for or decides, where the parties disagree, which dates are proposed and which are in effect. Every claim cites the page it came from, and code checks each quote against that page.

## What we found first

| Finding | Consequence |
| --- | --- |
| Public RECAP PDFs download from `storage.courtlistener.com` (Amazon S3 behind CloudFront) without a token and with no rate-limit headers. The bytes matched CourtListener's SHA1. | Downloads should not count against the API budget (5/min, 50/h, 125/day). We have not yet confirmed this with CourtListener. |
| For available documents, CourtListener already returns the extracted text (`plain_text`, OCR included), with one form feed per page. | Page-cited analysis works with no download. |
| `plain_text` is in layout mode, so the cells of a two-column table are interleaved, and a quoted cell such as "On or around July 17, 2028" is not contiguous. `pdftotext` without `-layout` keeps cells in reading order. | For documents with schedule tables, download the PDF and extract it with `layout=False`. |
| Only a small share of documents are available: 9 of 159 on the D. Mass. docket and 2 of 58 events stored in the cloud. None of them was a court order. | The approach works, but on these dockets coverage is limited by RECAP, not by our code. See "Open questions". |
| The entry prompt (M2) produced a vague two-sentence summary of a 14-page Rule 26(f) report, and turning on thinking did not fix it. The cause was the format: 300 characters, entry-level fields, and no disputes or proposed dates. | We added a separate document prompt and schema. |

## Design

```
document text (CourtListener plain_text, or local PDF via src.ingest.pdf)
  → pages → "[Page N]" marked input (whole pages up to llm.max_document_chars)
  → LLM (prompt document_v1, JSON mode)
  → parse_document: strict schema; over-long lists are cut, far longer ones are invalid
  → verify_document: per-claim quote and page check, date-in-quote check
  → Analysis.details["document"] → digest entry
```

- **Schema**: `document_type`, `overview` (400 characters), `key_points` (up to 5), `disputes` (an issue with each party's position, up to 6), `deadlines` (in effect, up to 15), `proposed_dates` (event, party and date, up to 40, most important first), `action`, and `confidence`. Every point, position and date carries a `quote` and a `page`.
- **Verification** ([src/llm/document.py](../src/llm/document.py)):
  - A claim is kept when its quote is on the page the model cited, or occurs exactly once elsewhere (the page is then corrected).
  - Dates must appear in their quote.
  - Matching ignores case, whitespace, curly quotes and hyphens, so "patents-in-\nsuit" matches "patents-in-suit".
  - Dropped claims are kept with a reason for auditing and are never shown to recipients.
  - Verification proves the quote and date are on that page. Which event or party a date belongs to is the AI's reading, and the email says so.
- **Analyzer** ([src/analyzers/document.py](../src/analyzers/document.py)): it subclasses the M2 `LLMAnalyzer`, so it shares the `llm_calls` audit trail, cache and daily token budget. A failure returns a status and no claims.
- **Cache key**: it now includes the prompt text and provider options. Before this change, editing a prompt without bumping its version, or switching thinking on, silently reused old answers. This changes the M2 entry analyzer's keys too: each cached entry is re-analyzed once.
- **Rendering**: when a briefing exists, its overview and action replace the entry reading. The entry is followed by key points, disputes, a "Proposed dates (not yet set by the court)" list that groups both sides' dates per event, and deadlines, all with `(p. N)`. Entry deadlines that the document does not cover are kept.

Not wired into the pipeline yet. Today it runs from [eval/run_document.py](../eval/run_document.py).

## Results on #39 (Joint Rule 26(f) report, D. Mass., 14 pages)

Prompt `document_v1`, `deepseek-flash`, from the downloaded PDF:

| | Thinking off | Thinking on |
| --- | --- | --- |
| Input / output tokens | ~7.1k / ~3.2k | ~7.2k / ~16k (needs `--max-output-tokens 32000`) |
| Latency | ~11 s | ~72 s |
| Cost (peak prices) | ≈ $0.006 | ≈ $0.021 |
| Claims dropped by verification | 0 | 0 |
| Trial, pretrial, claim construction, discovery cut-offs, dispositive motions | all, both sides, listed first | all, both sides, listed first |
| Conditions such as "(or 60 days after the claim construction ruling)" | omitted | included |
| Key points | relevant | more specific (Lutnick discovery via DOC/DOJ, 30(b)(6) counting) |
| Proposed dates | ~20 events | ~22 events (adds reply expert reports, pretrial disclosures, trial briefs) |

Every date was checked by hand against pages 10–12. The run before this prompt version, which used the M2 entry prompt, gave a two-sentence summary with no schedule.

Tuning history on this document:
1. Quotes had to be unique in the whole document. Short table cells such as "January 15, 2027" repeat, so they were dropped. Now a quote passes if it is on the cited page.
2. Layout-mode text broke table quotes. Fixed by extracting with `layout=False`.
3. A 24-item cap cut off the trial date, which came last in date order. The cap is now 40, the most important items are asked for first, and over-long lists are cut instead of rejected.
4. A past event ("exchanged initial disclosures by July 13") was listed as a deadline. A rule against this was added.
5. With thinking on, parties were called "Plaintiff" and "Defendant", copied from the prompt's own example. The example now uses party names, and a rule asks for the short names the document uses.
6. With thinking on, 16k output tokens were not enough: thinking tokens count toward `max_tokens`, and the JSON was cut off. The client now reports this as "LLM output reached max_tokens" instead of invalid JSON.
7. Two thinking calls of about 70 s failed with a dropped connection. A dropped connection, a timeout or a 5xx response is now retried once, for the M2 entry analyzer too. Both attempts are recorded in `llm_calls`.

This is one document. The prompt must not be tuned further on it alone.

## Next

1. **Evaluation set**: 15–20 real documents with labeled deadlines and proposed dates. They need to include court orders (scheduling orders, orders on motions), not only party filings. Terry downloads them by browser (CourtListener pages refuse automated fetches). The gate is precision and recall of at least 90% on deadlines and proposed dates, and no unverified claim in output.
2. **Thinking on or off**: decide on the evaluation set, not on one document.
3. **Pipeline wiring**:
   - Run the briefing only for Priority and Worth-a-look entries whose document became available, so a single event never triggers two briefings.
   - Prefer the downloaded PDF when the document has tables, and use `plain_text` otherwise.
   - Use a separate daily budget.
   - Store the result in `details["document"]`.
   - Shadow it first, as in M2.
4. **Long documents** (complaints run 60k–130k characters): today the text is cut after whole pages, and the email says "Read pages 1–N of M". Splitting the text into chunks and merging the results is a later step.
