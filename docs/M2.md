# Milestone 2: LLM Analysis

Started: 2026-10-24. Branch: `m2-llm`, stacked on `court-display-names`.

## Goal

Add an AI reading of every detected change: what happened, whether a lawyer needs to act, and any deadline. Every claim that can be checked is checked against the source text before a lawyer sees it.

Example of what an entry in the digest gains:

```
#1234 · Filed Oct 22, 2026 · NEW
ORDER granting in part and denying in part 1201 Letter Motion to Compel…
AI summary: The court partly granted plaintiffs' motion to compel output logs.
Action: Defendants must produce the requested output logs.
Deadline: Nov 5, 2026 — "shall produce the requested output logs by 11/5/2026"
```

## Decisions

| Topic | Decision |
| --- | --- |
| Where to build | Entirely local: a SQLite dev database, real data already on disk, and read-only exports from Supabase. No CourtListener calls from local runs. Then 1–2 days of shadow mode in the cloud before AI content reaches email. |
| Model | `deepseek-flash` through the existing `openai_compatible` adapter, with thinking mode disabled. The model is configuration only, so Qwen can be added later by changing settings. |
| Authority | The LLM can **raise** importance, and only with a verified evidence quote. It can never lower an item that the rules marked high. |
| Failure | Any LLM failure (network, empty or invalid JSON, budget) falls back to the rules result. Delivery is never blocked by the model. |
| Input | Entry description, document descriptions, and CourtListener's extracted `plain_text` when present, truncated to a fixed size. No extra API requests. Full PDF/OCR is Milestone 3. |
| Privacy | Only public court records are sent. Recipients and subscriptions are never sent. |
| Budget | 10 CNY prepaid. A per-run call cap and a per-day token cap are enforced from config. |
| Labels | Terry reviews the evaluation labels. A lawyer spot-check is optional. |

## Provider facts (checked 2026-10-23/24)

- DeepSeek base URL `https://api.deepseek.com`, OpenAI-compatible `/chat/completions`. Models: `deepseek-flash` and `deepseek-v4-pro`.
- `deepseek-flash` costs $0.30 per 1M input tokens (cache miss) and $1.20 per 1M output tokens at peak, half that off-peak. Peak is 01–04 and 06–10 UTC on weekdays. A cache hit is $0.006 per 1M input tokens.
- Thinking mode is **on by default**, and its tokens are billed as output. It must be disabled with the provider-specific body `{"thinking": {"type": "disabled"}}`. A live test confirmed this: no `reasoning_content`, a 0.8 s response, and usage reported with `prompt_cache_hit_tokens`.
- JSON mode needs `response_format: {"type": "json_object"}`, the word "json" in the prompt, an example, and a sensible `max_tokens`. The docs warn it can occasionally return empty content.
- Local data: 92 real entries for docket 73132799, with 159 documents. Only 9 documents have `plain_text`, averaging about 60k characters, so truncation matters.

### Gate before AI content reaches email

- Court-order recall at least as high as rules.
- Zero unverified deadlines in the final output.
- Deadline accuracy of at least 90% on labelled deadlines.
- Projected monthly cost within budget.

## Evaluation results (2026-10-24, local, labels still drafts)

Data: 78 real entries from docket 73132799 (D. Mass.), with 14 empty descriptions excluded. Labels were drafted by Claude and are pending review. Model `deepseek-flash`, thinking disabled.

| Metric | Rules | LLM, prompt v3 |
| --- | ---: | ---: |
| Priority (high) recall | 0% (0/8) | **88% (7/8)** |
| Priority precision | n/a | 88% |
| Exact importance match | 72% | 92% |
| Deadline precision / recall (6 labeled) | n/a | 100% / 100% |
| Unverified claims reaching output | n/a | 0 |
| Failed or invalid responses | n/a | 0 / 78 |
| Cost | n/a | $0.018 for 78 calls (about $0.0002 each) |

Findings:
- This court writes orders as `Judge William G. Young: ELECTRONIC ORDER …`, so the start-of-description rules missed **every** court order on the docket. The LLM is not an extra here; it is what makes this court usable.
- Prompt history: v1 extracted dates a party merely *requested* as deadlines (precision 67%). v2 fixed that but over-generalised and dropped transcript redaction deadlines (recall 67%). v3 clarifies both and passes every gate. All versions stay in `src/llm/prompts/` for audit.
- Terry resolved the borderline labels on 2026-10-24: an affidavit of service stating the answer date (#7) is high, assented motions for leave (#51, #54) are medium, clerk requests for courtesy copies (#59, #60) are medium, and a transcript with redaction deadlines (#77) is high. Rerun with those labels (cached, no cost): priority precision 100%, recall 89% (8/9), exact match 96%, deadlines 100% / 100%. The remaining misses are #7, #59 and #60, all scored low by the LLM.
- Caveat: one docket, one court, and the prompt was tuned on this set. Before cloud rollout, rerun on held-out entries from the M1 trial dockets (S.D.N.Y., W.D. Wash., N.D. Cal.).

Reproduce: `LLM_EXTRA_BODY='{"thinking":{"type":"disabled"}}' python eval/run_eval.py --dotenv`. Cached responses make reruns free.

## Heavy filing days (2026-10-24)

The first real cloud digest came from the OpenAI MDL on its summary-judgment opposition deadline: 50 entries listed one per line, 6 of them blank. Fixes, which apply with or without the LLM:

- **Grouped "Other activity"** ([src/notify/grouping.py](../src/notify/grouping.py)). Filings are grouped by type, with counts and sealed counts. Declarations list their declarants with volume ranges ("Davida Brook (Vols. 9–17)"), and one link opens the whole range on CourtListener. The same day now renders in 21 lines instead of about 60.
- **Entries without a description are deferred.** Detect records nothing until CourtListener supplies the text, and then reports the entry once, as new. Older blank events render as a single count.
- **Overflow is stated.** The headline says "N more in the next digest" when the per-digest cap applies.
- Long descriptions are cut at word boundaries.

## Cloud rollout (after label review and the held-out check)

1. Repository **variables**: `LLM_PROVIDER=openai_compatible`, `LLM_BASE_URL=https://api.deepseek.com`, `LLM_MODEL=deepseek-flash`, `LLM_EXTRA_BODY={"thinking": {"type": "disabled"}}`, and `ANALYZER=rules+shadow`. Repository **secret**: `LLM_API_KEY`.
2. Run 1–2 days in shadow mode, then compare `analyses` rows (`rules` vs `llm-shadow`) and check `llm_calls` spend.
3. Set `ANALYZER=llm`. AI content then appears in digests.

## Local workflow rules

1. Run the pipeline locally only with `--sqlite`. Never run a non-dry-run pipeline against Supabase from a laptop.
2. No CourtListener calls from local runs. The API quota belongs to the cloud pipeline.
3. `LLM_API_KEY` lives only in the local `.env` until cloud rollout, and then in a GitHub secret.
